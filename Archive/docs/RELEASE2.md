# Release 2: fewer Surfline requests, fresh daily data, incomplete-draft notes

This update builds on Release 1 and includes the editable location name, Telegram recovery commands and five-option approval message. It does not enable Open-Meteo, `/refresh`, or change the 03:07 Bali generation time. No Cloudflare deploy, D1 migration or new secret is required.

## Install

1. Extract the update ZIP. Copy its files into `main`, keeping their paths, especially `.github/workflows/surf-review.yml`, `.github/workflows/surfline-check.yml`, and `tests/`. Use one upload/commit so the workflow and Python files agree. Do not upload to `review-state`. The bot creates `fetch-attempt.json` there itself. Do not replace `state.json`, reset history, or clear uncertain sends.
2. Wait for Python and Worker checks on `main` to pass. No repository variables are required for the defaults. Optional repository **variables** (not secrets): `SURF_REQUEST_PROTECTION=false` pauses new provider fetches rather than returning to aggressive retries; `SURF_INCOMPLETE_DRAFTS=false` withholds incomplete drafts; `SURF_STATE_RETENTION=false` disables report-detail trimming. Keep existing webhook, review and Telegram settings.
3. Let the next 03:07 run proceed normally. There is no need to resend a published report or run the live diagnostic. Look for HTTP attempts and cache hits in the Actions summary. A healthy first run may have zero cache hits: each new day starts fresh. Reply to the latest approval message normally.

## What happens

- For each spot, endpoint and target-day cycle, at most two actual requests are reserved: the first attempt and one retry. A 403 can use the tested minimal plain request immediately as its **one** retry, not an extra retry. There is no third transport attempt. A 429 stops new requests and honours `Retry-After` across runs. Temporary failures get a five-minute wait; a retry cannot start outside the 30-minute cycle. Requests are spaced at least three seconds apart.
- Each reservation is committed before calling Surfline; each successful response is committed before moving on. A cancelled request still consumes its attempt. A failed checkpoint stops fetching. State pushes can increase healthy-run duration: this release prioritises fewer duplicate requests over shortest elapsed time. The live diagnostic uses the same workflow concurrency, state checkout, cooldowns and next-day request budget. Legacy local transport tests still exercise historical fallback behaviour; Actions uses the protected path.
- Only actual responses are cached; the two-day fallback is stored under its actual parameters. Scope includes spot, endpoint, query/units and daily cycle. Older responses and previous target dates cannot feed a new morning generation. Final snapshots record per-endpoint capture time; all captures must fit within 30 minutes and be at most 30 minutes old. Provider issue time may differ from request time.
- A retryable gap leaves generation pending. The workflow can show a failed retry-pending run; the existing Worker recovery (or poll schedule) wakes a later run. If required daylight breaking-surf data is unavailable after the retry opportunity, send one failure notice for that date. If an entire freshness window was missed, never issue a report from stale data. Do not reset the ledger to force another attempt.
- Other missing inputs allow a draft. The review prompt ends with plain-language notes identifying the missing input and affected assessment. The notes refer only to Surfline; no second provider was checked. Sunrise/sunset unavailable with actual breaking-surf data gives a draft with unassessed time windows. Approval, memory, cancellation, uncertain-send and publication safeguards still apply.
- At state saves, completed published/expired reports older than seven days have bulky forecast/feedback/history fields trimmed. The record, publication IDs and a digest remain. Active reports, uncertain sends and global remembered instructions remain intact. Subsequent fetches discard previous days’ reusable payloads and drop old attempt cycles. This is logical trimming of the current files, **not deletion from public Git history**.

## Rollback

Pause new live fetches with `SURF_REQUEST_PROTECTION=false` while investigating. For a full rollback, pause `SURF_REVIEW_ENABLED`, restore the prior code and both prior workflow files together, then re-enable when ready, respecting any outstanding provider cooldown. Leave `review-state/state.json` and `review-state/fetch-attempt.json` in place. Turning off retention prevents future trimming; it cannot restore already-trimmed details. The earlier files remain in Git history. No Worker rollback is needed for Release 2.
